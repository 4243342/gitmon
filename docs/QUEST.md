# 任务模式 · 设计文档

状态：草案（待评审）。与 `docs/STORY.md`（剧情模式）并列，互不占用。

> 相关实现：`src/engine.js`（judge 的体检分项）、`src/scan.js`（仓库快照）、
> `src/llm.js`（模型绑定）、`docs/SSOT.md`（同步契约）

## 1. 定位

剧情模式是一次性的主线远征；**任务模式是可重复的日常副本**。

一句话说清玩法：

> **AI 指出你项目里的真问题，你去改；改完 AI 复审，确认改好了才发奖励。**

奖励对应的是「真的修掉了一个问题」，不是点一下领取，也不是做选择题。

## 2. 与剧情模式的边界

| 维度 | 剧情模式 | 任务模式 |
|---|---|---|
| 时长 | 一次远征（三章） | 单任务 1–3 天（改代码 + 复审） |
| 频率 | 同时只能有一条（C1） | 同时最多 3 个进行中任务，每日可领 3 个 |
| 绑定 | 锁桌宠 | 不碰桌宠 |
| 前置 | AI 高级模式 + AI 认证精灵 | AI 认证精灵 + 该仓库的写权限 |
| 产出 | 称号、结局剧情 | 经验、词条材料、审查积分 |

**前提**：任务对象必须是玩家有权修改的仓库（自己的项目或自己 fork）。审不了别人的仓库，因为改不了。

## 3. 核心循环

```
① 领取任务
   AI 读仓库快照，指出一个真实短板，给出「问题描述 + 修复方向 + 验收标准」
   ↓
② 玩家改代码
   在本地 / GitHub 上真实修改并推送
   ↓
③ 提交复审
   点「我改好了」→ 后端重新拉取最新快照
   ↓
④ AI 复审
   结构核对（快照事实）→ 内容抽查 → 必要时 diff 复审
   ↓
通过 → 发奖励，任务关闭
不通过 → 返回「还差什么」的具体证据，可继续改、可重试
```

复审最多 5 次，超过后任务作废（防止用试错代替思考），但记录保留。

## 4. 任务从哪来

不凭空出题，全部取自 `judge()` 体检分项里的真实短板，且**必须可机器验收**：

| 短板 | 任务目标（可判定） | 验收级别 |
|---|---|---|
| `hasTests = false` | 根目录出现测试目录，且目录下 ≥3 个测试文件 | L1 + L2 |
| `hasCI = false` | `.github/workflows` 下出现 ≥1 个可解析的 workflow（含 `on:` 与 ≥1 个 `jobs.*.steps`） | L1 + L2 |
| `hasDocs = false` | 出现 `docs/` 或根目录文档，且 ≥800 字 | L1 + L2 |
| `hasLockfile = false` | 根目录出现任一 lockfile | L1 |
| `hasDocker = false` | 出现可解析的 Dockerfile（含 FROM 与 CMD/ENTRYPOINT） | L1 + L2 |
| `daysSincePush > 180` | 目标仓库出现新的推送（7 天内） | L1 |
| `openIssues > 100` | issue 数下降 ≥20% 或新增标签分类 | L1 |

各分项都达标的健康仓库出「防守型任务」：让模型挑一处代码坏味道，玩家修掉后有 diff 复审（L3）。

## 5. 验真机制（本模式的核心）

三级验真，逐级加严。**结论以事实为准，模型只负责解释**。

### L1 结构核对

重新拉取仓库快照，比对目标字段是否由不满足变为满足。

- 数据来源：与 `scan.js` 同一套 GitHub 接口
- 用冻结的判定函数，不允许模型改判定
- 输出 `evidence`：`{ field, before, after }`

### L2 内容抽查

防止「建个空目录骗过检查」：

| 目标 | 最低内容要求 |
|---|---|
| 测试目录 | ≥3 个测试文件，且至少 1 个命中断言关键字（`assert` / `expect` / `should` / `t.Run` / `#[test]`） |
| workflow | 能解析出 `on:` 触发器与 ≥1 个 step |
| 文档 | ≥800 字，且不是纯目录列表 |
| Dockerfile | 含 `FROM` 与 `CMD` 或 `ENTRYPOINT` |

内容抽查用正则与行数统计，**不调模型**——可复现、可测试。

### L3 模型复审

只用于结构上无法判定质量的任务（如「消除这处坏味道」）：

1. 取默认分支的最新 diff（或目标文件内容）
2. 模型输出 `{ fixed: boolean, reason, leftover }`
3. `fixed=false` 时把 `leftover` 原样回传玩家，作为「还差什么」

模型超时或不可用 → 该类任务不出题；已出的任务转为「仅 L1/L2 判定」并降低奖励档位。

### 复审结果的三态

| 结果 | 含义 | 处理 |
|---|---|---|
| `passed` | 全部检查通过 | 发全额奖励 |
| `partial` | L1 通过但 L2 不足 | 发 40% 奖励，可继续改 |
| `failed` | 结构仍未达标 | 不发奖励，返回证据 |

## 6. 反作弊

1. **不允许审别人的仓库**：任务只从自己收藏且有写权限的项目里出
2. **空壳防御**：L2 内容抽查（§5）
3. **同一问题 30 天内不重复出**：`(owner_key, pet_key, goal_key)` 唯一约束
4. **复审次数上限 5 次**，超过作废
5. **commit 必须晚于任务领取时间**：防止拿历史提交冒充新修复
6. **奖励只发一次**：`quest_runs.reward` 落库后重复提交不再发放

## 7. 数据模型

新增表 `quest_runs`（后端 SQLite，属 SSOT）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 任务实例 ID |
| `owner_key` | TEXT | 归属，与 `pets.owner_key` 同规则 |
| `pet_key` | TEXT | 目标仓库，`platform-fullName` |
| `goal_key` | TEXT | 目标键，如 `tests` / `ci` / `docs` / `smell:<file>` |
| `verify_level` | TEXT | `L1` / `L12` / `L123` |
| `payload` | TEXT | JSON：问题描述、修复方向、验收标准、出题时的事实快照 |
| `issued_at` | REAL | 领取时间（用于校验 commit 时间） |
| `attempts` | INTEGER | 已复审次数，上限 5 |
| `status` | TEXT | `fixing` / `passed` / `failed` / `expired` |
| `evidence` | TEXT | JSON：每次复审的 `{before, after, missing}` |
| `reward` | TEXT | JSON：实际发放的奖励 |
| `verify_at` | REAL | 最近一次复审时间 |

约束：

```sql
CREATE UNIQUE INDEX ux_quest_goal
  ON quest_runs(owner_key, pet_key, goal_key, date(issued_at));
```

## 8. 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/quest/board` | 今日可接任务（按短板推荐 3 个，含验收标准预览） |
| `POST` | `/api/quest/issue` | 领取 `{ pet, goal_key }`，返回问题描述与修复方向 |
| `POST` | `/api/quest/verify` | 提交复审 `{ id }`，重新扫描并返回 `passed/partial/failed` 与证据 |
| `GET` | `/api/quest/history` | 历史记录、通过率、复审次数分布 |

`verify` 由玩家主动触发，每次触发都重新扫描（可缓存 2 分钟，避免连点刷接口）。

## 9. 奖励与限额

| 结果 | 经验 | 材料 | 审查积分 |
|---|---|---|---|
| `passed` | 100% | 30% 概率掉词条材料 | +3 |
| `partial` | 40% | 无 | +1 |
| `failed` | 0 | 无 | 0 |

- 难度系数：L1=1.0、L1+L2=1.2、L1+L2+L3=1.5
- 同时进行中最多 3 个任务，每日可领 3 个
- 审查积分可兑换：重新鉴定券、剧情模式「换一批」次数

| 项目 | 星标 | 套用了什么 | 协议 |
|---|---|---|---|
| [CleverRaven/Cataclysm-DDA](https://github.com/CleverRaven/Cataclysm-DDA) | 13.5k | 任务定义的五段式 `goal / end / fail / reward / dialogue`，以及「失败有单独结算」的处理；本设计 §7 `payload` 与 §5 三态结果照此拆分 | 代码与内容 CC-BY-SA，仅参考字段设计 |
| [OpenRCT2/OpenRCT2](https://github.com/OpenRCT2/OpenRCT2) | 16.6k | 关卡结构：**目标 + 约束 + 时限 + 分档奖励**；本设计把它压成单任务的三档奖励（§9） | GPL-3.0，仅参考机制 |

选它们的理由：两套任务系统都被玩家验证了十年以上，且**完全数据驱动**——任务写在配置里而不是硬编在代码里。
我们要的正是这个形状：加一种任务只需要加一条配置，不用改引擎。

## 11. 验收标准

1. 任务只从真实短板出，出题时的事实快照随 `payload` 落库
2. 未持有写权限的仓库不出现在可选列表
3. 复审前必须存在晚于 `issued_at` 的新提交，否则直接 `failed` 并说明原因
4. 建空测试目录无法通过 L2（文件数 <3 或无断言关键字）
5. 空白文档（<800 字或纯目录）无法通过 L2
6. 同一 `(owner, pet, goal_key)` 30 天内不重复出题
7. 复审第 6 次返回 429，任务转 `expired`
8. `passed` 后重复提交不重复发奖励
9. 模型不可用时，L3 类任务不出题；已出的转 L1/L2 并降档
10. 复审响应里的 `missing` 能明确指出还差哪一项，而不只是一句「未通过」

## 12. 未决问题

1. **写权限怎么确认**：要求玩家授权 GitHub 写 scope，还是只凭「仓库在自己名下」推断？
2. **扫描成本**：每次复审要重扫仓库（约 5 次 API 调用），每日 3 任务 × 5 次复审的上限是否够用
3. **积压任务**：玩家领了不改，3 个名额会被占满；是否要加 72 小时自动过期
