## 0. 已上线：给作者的仓库点一颗星

这是第一个上线的活动任务，也是本模式机制的一个最小完整闭环 ——
**领取 → 做一件事 → 复审 → 发奖**，每一步都有事实依据，不靠模型点头。

### 玩法

1. **领取**：任务板从「社区里别人孵化过的精灵仓库」里给一个目标，
   后端**现拉一次**它的星数记下来作为基线。
2. **去点星**：玩家自己去 GitHub / Gitee 点 ★。前端不代劳，只给外链。
3. **复审**：后端重新拉一次星数比对。涨了才算数。

### 验真（两层）

| 层 | 做什么 | 数据来源 |
|---|---|---|
| **L1 结构核对** | 领取时的 `stargazers_count` 作基线，复审时重新拉，看是不是真涨了 | `GET /repos/{owner}/{repo}` |
| **L2 归因核对** | 确认「这次点星确实是**本人**做的」，防止蹭别人的星混过去 | `GET /user/starred/{owner}/{repo}` → 204 已收藏 / 404 没收藏 |

两个平台都有对应的收藏查询接口，所以 GitHub 与 Gitee 都能做 L2。
归因必须用**玩家自己的**令牌（`X-GitHub-Token` / `X-Gitee-Token` 头或登录会话）：
服务端兜底令牌代表的是站点账号，问出来的是「站点收藏了没」，跟玩家无关。

### 三态判定与奖励

| 结果 | 条件 | 奖励 |
|---|---|---|
| `passed` | L1 通过 **且** L2 确认是本人点的 | 星尘 40 + 词条碎片 1 |
| `partial` | L1 通过但 L2 不足（没令牌 / 令牌说没收藏过） | 星尘 16（40%），可继续复审 |
| `failed` | L1 不通过（星数没涨） | 无 |

`partial` 之所以还发 40%：星数确实涨了是事实，只是「是本人点的」这层没钉死。
补上令牌再复审一次就能**补齐差额**升到 `passed`（不重发，走 `source_key` 幂等）。

### 为什么点星是个好任务

引擎里 `community = lognorm(snapshot.stars, 20000) * 60.0`（质量分占 15% 权重），
`growth.py` 的 `XP_RULES["star"] = (1, 120)` 也吃星数 ——
玩家点的这颗星会真的让那只精灵变强，形成「点星 → 精灵变强」的正反馈。

### 限额与反作弊

- 每日可领 3 个，同时最多压 3 个没复审的任务
- 同一仓库 30 天内不重复出题（`quest_runs` 唯一索引 + 冷却期判定）
- 复审上限 5 次，第 6 次任务作废
- 奖励只发一次：`source_key = quest:{run_id}:{item}:{tier}`


## 1. 定位

剧情模式是一次性的主线远征；**任务模式是可重复的日常副本**。

一句话说清玩法（下一阶段形态）：

> **AI 指出你项目里的真问题，你去改；改完 AI 复审，确认改好了才发奖励。**

奖励对应的是「真的修掉了一个问题」，不是点一下领取，也不是做选择题。

已上线的点星活动任务走的是同一套机制（领取 → 做 → 复审 → 发奖），
只是「做」那一步从改代码换成了点一颗星 —— 见 §0。

## 2. 与剧情模式的边界

| 维度 | 剧情模式 | 任务模式 |
|---|---|---|
| 时长 | 一次远征（三章） | 单任务 1–3 天（改代码 + 复审）；点星任务是几分钟 |
| 频率 | 同时只能有一条（C1） | 同时最多 3 个进行中任务，每日可领 3 个 |
| 绑定 | 锁桌宠 | 不碰桌宠 |
| 前置 | AI 高级模式 + AI 认证精灵 | AI 认证精灵 + 该仓库的写权限（点星任务无此要求） |
| 产出 | 称号、结局剧情 | 经验、词条材料、审查积分 |

**前提**（下一阶段形态）：任务对象必须是玩家有权修改的仓库（自己的项目或自己 fork）。
审不了别人的仓库，因为改不了。点星活动任务的对象**恰恰是别人的仓库** ——
它给别人的仓库点星，不改任何代码。

## 3. 核心循环

```
① 领取任务
   AI 读仓库快照，指出一个真实短板，给出「问题描述 + 修复方向 + 验收标准」
   ↓
② 玩家改代码
   在本地 / GitHub 上真实修改并推送
   ↓
③ 提交复审
   点「我改好了」→ 后端重新拉取最新快照
   ↓
④ AI 复审
   结构核对（快照事实）→ 内容抽查 → 必要时 diff 复审
   ↓
通过 → 发奖励，任务关闭
不通过 → 返回「还差什么」的具体证据，可继续改、可重试
```

复审最多 5 次，超过后任务作废（防止用试错代替思考），但记录保留。

## 4. 任务从哪来

不凭空出题，全部取自 `judge()` 体检分项里的真实短板，且**必须可机器验收**：

| 短板 | 任务目标（可判定） | 验收级别 |
|---|---|---|
| `hasTests = false` | 根目录出现测试目录，且目录下 ≥3 个测试文件 | L1 + L2 |
| `hasCI = false` | `.github/workflows` 下出现 ≥1 个可解析的 workflow（含 `on:` 与 ≥1 个 `jobs.*.steps`） | L1 + L2 |
| `hasDocs = false` | 出现 `docs/` 或根目录文档，且 ≥800 字 | L1 + L2 |
| `hasLockfile = false` | 根目录出现任一 lockfile | L1 |
| `hasDocker = false` | 出现可解析的 Dockerfile（含 FROM 与 CMD/ENTRYPOINT） | L1 + L2 |
| `daysSincePush > 180` | 目标仓库出现新的推送（7 天内） | L1 |
| `openIssues > 100` | issue 数下降 ≥20% 或新增标签分类 | L1 |

各分项都达标的健康仓库出「防守型任务」：让模型挑一处代码坏味道，玩家修掉后有 diff 复审（L3）。

## 5. 验真机制（本模式的核心）

三级验真，逐级加严。**结论以事实为准，模型只负责解释**。

### L1 结构核对

重新拉取仓库快照，比对目标字段是否由不满足变为满足。

- 数据来源：与 `scan.js` 同一套 GitHub 接口
- 用冻结的判定函数，不允许模型改判定
- 输出 `evidence`：`{ field, before, after }`

### L2 内容抽查

防止「建个空目录骗过检查」：

| 目标 | 最低内容要求 |
|---|---|
| 测试目录 | ≥3 个测试文件，且至少 1 个命中断言关键字（`assert` / `expect` / `should` / `t.Run` / `#[test]`） |
| workflow | 能解析出 `on:` 触发器与 ≥1 个 step |
| 文档 | ≥800 字，且不是纯目录列表 |
| Dockerfile | 含 `FROM` 与 `CMD` 或 `ENTRYPOINT` |

内容抽查用正则与行数统计，**不调模型**——可复现、可测试。

### L3 模型复审

只用于结构上无法判定质量的任务（如「消除这处坏味道」）：

1. 取默认分支的最新 diff（或目标文件内容）
2. 模型输出 `{ fixed: boolean, reason, leftover }`
3. `fixed=false` 时把 `leftover` 原样回传玩家，作为「还差什么」

模型超时或不可用 → 该类任务不出题；已出的任务转为「仅 L1/L2 判定」并降低奖励档位。

### 复审结果的三态

| 结果 | 含义 | 处理 |
|---|---|---|
| `passed` | 全部检查通过 | 发全额奖励 |
| `partial` | L1 通过但 L2 不足 | 发 40% 奖励，可继续改 |
| `failed` | 结构仍未达标 | 不发奖励，返回证据 |

## 6. 反作弊

1. **不允许审别人的仓库**：任务只从自己收藏且有写权限的项目里出
2. **空壳防御**：L2 内容抽查（§5）
3. **同一问题 30 天内不重复出**：`(owner_key, pet_key, goal_key)` 唯一约束
4. **复审次数上限 5 次**，超过作废
5. **commit 必须晚于任务领取时间**：防止拿历史提交冒充新修复
6. **奖励只发一次**：`quest_runs.reward` 落库后重复提交不再发放

## 7. 数据模型

新增表 `quest_runs`（后端 SQLite，属 SSOT）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 任务实例 ID |
| `owner_key` | TEXT | 归属，与 `pets.owner_key` 同规则 |
| `pet_key` | TEXT | 目标仓库，`platform-fullName` |
| `goal_key` | TEXT | 目标键，如 `tests` / `ci` / `docs` / `smell:<file>` |
| `verify_level` | TEXT | `L1` / `L12` / `L123` |
| `payload` | TEXT | JSON：问题描述、修复方向、验收标准、出题时的事实快照 |
| `issued_at` | REAL | 领取时间（用于校验 commit 时间） |
| `attempts` | INTEGER | 已复审次数，上限 5 |
| `status` | TEXT | `fixing` / `passed` / `failed` / `expired` |
| `evidence` | TEXT | JSON：每次复审的 `{before, after, missing}` |
| `reward` | TEXT | JSON：实际发放的奖励 |
| `verify_at` | REAL | 最近一次复审时间 |

约束：

```sql
CREATE UNIQUE INDEX ux_quest_goal
  ON quest_runs(owner_key, pet_key, goal_key, date(issued_at, 'unixepoch'));
```

`'unixepoch'` 修饰符**不能省**：`date()` 不认 Unix 时间戳，省了表达式恒为 `NULL`，
唯一索引形同虚设。

也不能写成 `date(issued_at, 'unixepoch', 'localtime')`：带时区换算的 `date()`
在 SQLite 里是非确定性函数，索引能建出来，但 **INSERT 会直接报**
`non-deterministic use of date() in an index`。

「同一个仓库 + 同一种任务，一天只能领一次」这条硬约束另有归属：
索引里的 `date()` 按 UTC 日界切，本地自然日由业务层用纪元秒区间做
（`quest._today_range`，`time.mktime` 算当日零点）。细节见 `docs/SSOT.md` §5。

## 8. 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/quest/board` | 任务板：活动任务定义、今日额度、可领目标、进行中的任务 |
| `POST` | `/api/quest/issue` | 领取 `{ goal_key, target }`，记下目标当前星数作为基线 |
| `POST` | `/api/quest/verify` | 复审 `{ id }`，重新拉星数比对，返回 `passed/partial/failed` 与证据 |
| `GET` | `/api/quest/history` | 历史记录、通过率 |

字段级契约见 `docs/SSOT.md` §4。

`verify` 由玩家主动触发，每次触发都重新拉一次目标仓库的元信息
（一次请求，不复用全量扫描的十几个请求）。

（`key` / `title` / `brief` / `accept` / `verify_level` / `max_attempts` /
`daily_limit` / `cooldown_days` / `reward`），接口与状态机完全复用。
加一种新任务 = 加一条配置 + 一个候选池选择器，不动引擎、不动前端。

## 11. 工程要点（踩过的坑）

几处不写下来就会再踩的：

1. **归属键的冒号留不住**。`api.py::owner_key` 对 `X-Gitmon-User` 头做
   `[^A-Za-z0-9_-]` 清洗，冒号会被删掉 —— `user:github:tester` 走请求头会变成
   `usergithubtester`。只有登录会话路径才保留 `user:` 前缀。
   候选池要排除「作者就是玩家本人」的仓库时，得直接调业务函数测这一层。

2. **SQLite 的 `date()` 有三个坑**（详见 `docs/SSOT.md` §5）：
   `date(REAL)` 不认纪元秒；`date('now','unixepoch')` 恒为 `NULL`；
   带 `'localtime'` 的 `date()` 是非确定性函数，写进索引后 INSERT 直接报错。

3. **冷却期不能写成「永久屏蔽」**。候选池最初查的是全部历史记录，
   结果冷却期一过，那个仓库就再也回不来了。正确口径是
   `issued_at > cutoff OR status = 'fixing'` —— 冷却期满自动回池，
   进行中的任务继续占位。

4. **错误提示要说真话**。冷却期检查必须排在候选池检查**之前**：
   冷却中的仓库本来就不在池子里，先查池子会把「冷却中」误报成「不在任务列表」。

5. **令牌必须按平台分流**。归因核对要问「这个账号收藏过它没」，
   拿 Gitee 令牌去问 GitHub 是问不出结果的。
   `scanner/tokens.py` 用令牌前缀挡住跨平台串令牌；
   `quest_api.py` 的 `platform_tokens` 把两个平台的令牌分桶。

6. **`GET /user/starred/{owner}/{repo}` 的 204/404 都是有效答案**，
   不是错误。`HttpClient.get` 加了 `accept=(204, 404)` 参数让它们不进异常通道。

7. **前端不判定、不算账**。星数、通过没通过、奖励多少全在后端，
   前端只把结果原样显示。发奖走 `inventory.grant`（`source_key` 幂等），
   前端拿到结果后只调一次 `loadInv()` 刷新背包。

## 12. 验收标准

### 已上线（点星活动）—— 后端 22 项用例 + 真浏览器 E2E 33 项全绿

1. 星数没涨 → `failed`，不发任何奖励
2. 星涨了但归因查不出来（没令牌）→ `partial`，只发 40%
3. 星涨了且归因确认是本人点的 → `passed`，发全额
4. `partial` 补上令牌再复审 → 补齐差额升 `passed`，不重复发
5. 已 `passed` 的任务重复提交 → 返回 `duplicate: true`，余额不变
6. 复审第 6 次 → 429，任务转 `expired`
7. 同一仓库 30 天内不能重复领（冷却期）
8. 不在候选池里的仓库不能领（否则就是随便找个热门仓库刷奖励）
9. 今日额度 3 个用尽后返回 429
10. 手上压满 3 个没复审的任务时不能再领
11. 复审过的任务不再占待办名额
12. 别人的任务不能复审（404）
13. 复审响应里的 `missing` 能明确指出还差什么，而不只是一句「未通过」
14. 玩家自己名下的仓库、作者就是玩家本人的仓库不出现在候选池

### 下一阶段（AI 复审改代码）

1. 任务只从真实短板出，出题时的事实快照随 `payload` 落库
2. 未持有写权限的仓库不出现在可选列表
3. 复审前必须存在晚于 `issued_at` 的新提交，否则直接 `failed` 并说明原因
4. 建空测试目录无法通过 L2（文件数 <3 或无断言关键字）
5. 空白文档（<800 字或纯目录）无法通过 L2
6. 模型不可用时，L3 类任务不出题；已出的转 L1/L2 并降档

## 13. 未决问题

1. **写权限怎么确认**：要求玩家授权 GitHub 写 scope，还是只凭「仓库在自己名下」推断？
2. **扫描成本**：每次复审要重扫仓库（约 5 次 API 调用），每日 3 任务 × 5 次复审的上限是否够用
3. **积压任务**：玩家领了不改，3 个名额会被占满；是否要加 72 小时自动过期
4. **点星任务的边际收益**：每个仓库只能被一个玩家点一次星（30 天冷却），
   社区规模上去之后候选池会不会不够 —— 需要看真实数据
