# GPI 品质评估：70% 技术 + 30% 商业（阶段一）

> 状态：**启发式、待校准**。本版本不是经过 180/365 天回测验证的未来预测。
> 只替换新扫描云卡的六档品质来源；不修改等级、六维战力、卡盒、包装或立绘。

## 评分口径

总分 = 0.22 × 有效演进 + 0.18 × 工程可靠 + 0.16 × 架构 +
0.14 × 创新 + 0.15 × 需求 + 0.10 × 生态 + 0.05 × 可持续性。

分档：0～39 N、40～59 R、60～79 SR、80～89 UR、90～96 SE、97～100 PSE。

- 复用已有的 `RepoSnapshot`、`card_quality.Check` 源码检查、测试检查、文档检查、最近 52 周提交统计。
- **未知不按零分处理**：未验证信号向中性先验 50 收缩，并降低置信度。
- 源码证据覆盖率低于 30%，或整体证据置信度低于 25%，品质返回 `pending`，不发放猜测的高档卡。
- Star/Fork 仅为真实采用和生态的**弱代理**。不等于活跃用户或收入。
- 缺少独立技术创新验证时，创新分使用先验 50、置信度 0。提交多、CI 配置存在和 PR 合并并非真实质量证明。
- `potential.dimensions` 保留完整七维及权重、证据置信度和版本。经典卡面五条进度条展示四项技术 + 30% 商业加权汇总，不改变卡面结构。
- `rarity` API 字段在新云卡中作为六档品质兼容字段；旧 `qualityRating` 八档只负责源码审计及选图。旧存档没有 `potential` 时继续显示其既有品质，刷新扫描后才能切换到新公式。
- 单包多卡继续取已确认卡的最高六档品质；不改品质对应的模型立绘。
- 云卡数据出站保留 `communityRarity`，用于追溯旧的 Star/Fork 档位，不能把它当作 GPI。

## 为什么现在还不应该直接合入生产

此阶段**未**从 Gitee 的 `git_test` 直接移植源码（未能读取并核查仓库代码与许可证）。
已复用的是 GitMon 现有静态源码证据和扫描契约，而不是复制未知许可的实现。

目前只接入**新云卡**，本地扫描和 AI 高级入口仍用旧公式。
没有真实用户/留存/收入证据、同类仓库基准、30/90/180 天可靠快照差分、固定 SHA 工具运行结果，也没有校准回测，所以完整七档覆盖能力和 180/365 天预测准确率都未验证。不能声称迁移完成。

待验收：
1. `cd backend && python -m pytest tests/test_gpi_quality.py -q`
2. `cd backend && python -m pytest -q`
3. `npm ci && npm run test:quality && npm run build`
4. 云卡新扫描、旧收藏读回、确认/待评估、整箱排序、PNG 导出及 5 条进度条视觉。
5. 复核 Gitee `git_test` 的代码许可与固定提交采集实现，优先通过明确接口复用成熟模块。
6. 历史样本回测并校准阈值与同类项目分布，在此之前不要将启发式分数宣称为“未来预测”。

阶段二才统一本地和 AI 入口及真实长期证据采集，并增加回归测试后合入主线。
