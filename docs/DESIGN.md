# GitMon —— GitHub/Gitee 仓库精灵 · 产品设计文档

> 版本：v0.5
> 日期：2026-11-08
> 形态：Web 应用 | 数据源：GitHub + Gitee | 核心玩法：开卡包 → 养成进化
>
> 变更（v0.5）：新增 **§6.3 根基**、**§6.4 性格词条**、**§12 离线 AI 味检测工具**；
> 明确"AI 率只压根基、不压品质"的数值边界；数据模型与 MVP 同步。

---

## 1. 产品概述

**GitMon** 是一个把代码仓库"孵化"为宝可梦式精灵的 Web 应用。

用户输入任意 **GitHub 或 Gitee** 仓库地址，系统扫描仓库后将其转化为一个**卡包**——打开卡包的瞬间，精灵破壳而出：

- **品种（种族/属性）** 由技术栈 + 项目类型决定
- **品质（稀有度）** 由代码质量决定
- **初始等级** 由工程量决定

开包即入册，此后仓库的每一次提交、每一个 release，都化为精灵的经验值，推动它升级与进化。

**一句话定位**：你的仓库，是一只活着的精灵；开包那一刻，它破壳而出。

## 2. 核心流程：从仓库到精灵

```
用户输入仓库 URL（GitHub / Gitee 自动识别）
        │
        ▼
┌─ 扫描引擎 ─────────────────────────────────────┐
│  ① 技术栈扫描：语言占比、框架依赖、项目类型       │
│  ② 工程量估算：代码行、文件数、commit、贡献者     │
│  ③ 代码质量评估：测试、CI、文档、复杂度、活跃度   │
└────────────────────────────────────────────────┘
        │
        ▼
生成「卡包」（卡包外观 = 品质预告，SSR 卡包金光闪闪）
        │
        ▼
用户点击「开包」→ 开包动画 → 精灵破壳登场
（品种 + 品质 + 初始等级 + 六维能力 + 技能）
        │
        ▼
进入「我的图鉴」，开始养成
```

### 2.1 双平台支持

| 平台 | 识别方式 | API |
|---|---|---|
| GitHub | `github.com/owner/repo` | GitHub REST/GraphQL API |
| Gitee | `gitee.com/owner/repo` | Gitee OpenAPI v5 |

统一抽象为 `RepoScanner` 接口，两平台各自实现，产出标准化的 `RepoSnapshot` 数据结构，后续判定逻辑与平台无关。

### 2.2 确定性原则

- 同一仓库同一时期的扫描结果生成**同一只精灵**：以 `platform/owner/repo` + 数据哈希为随机种子，不允许"刷初始"。
- 重新扫描只会更新等级/品质（养成结果），不会改变品种。

### 2.3 账号维度：一整箱卡包（已实现）

输入粒度决定产出形态：

| 输入 | 产出 | 说明 |
|---|---|---|
| `github.com/owner/repo` | **一个卡包** | 单个项目的品质、等级 |
| `github.com/owner`（账号 / 组织主页） | **一整箱卡包** | 该账号拥有的每个项目各一包，品质各算各的 |

- 账号 → `GET /users/{owner}/repos`（Gitee 同理）拉项目清单，**排除 fork 与空仓库**，按最近活跃排序；
- 每个项目独立走完整扫描 + 判定（`judge(snapshot)`），互不影响——一个大项目不会抬高隔壁小项目的品质；
- 卡箱外观即"品质预告"：SSR 包金框 + 呼吸光，N 包灰框；未开的包显示 "?" 封印，开过的显示精灵；
- 支持点开任意一包（完整开包动画）或"一键全开"（逐张翻面）后批量收入图鉴；
- 匿名 GitHub API 60 次/小时，每项目约 5 个请求：无 Token 时默认只开最近活跃 6 个，有 Token 30 个；限流即停并明确提示，**绝不静默降级品质**；
- 确定性不变：种子仍是 `platform/owner/repo`，同一账号重复孵化只会更新数值，不会换精灵。

## 3. 品种体系（技术栈 + 项目类型）

精灵的"品种"由两个维度交叉决定：**元素属性**（主语言）× **生态类型**（项目类型）。

### 3.1 元素属性 —— 由主语言决定

| 主语言 | 元素属性 | 气质设定 |
|---|---|---|
| Python | 水 | 柔韧多变，数据与 AI 之灵 |
| JavaScript/TypeScript | 雷 | 敏捷爆发，无处不在 |
| Rust | 钢 | 坚硬安全，难以驯服但极可靠 |
| Go | 地 | 朴实稳重，并发之力 |
| Java | 岩 | 厚重耐久，企业级巨兽 |
| C/C++ | 火 | 原始强大，难以掌控 |
| Swift/Kotlin | 风 | 轻快现代，移动之翼 |
| Ruby/PHP | 草 | 优雅治愈，注重幸福感 |
| Shell/其他 | 普通 | 平平无奇，潜力未知 |

> 双语言仓库（占比均 >30%）生成**双属性精灵**。

### 3.2 生态类型 —— 由项目类型决定

通过依赖清单、目录结构、README 关键词、平台 topic 标签判定：

| 项目类型 | 精灵类型 | 判定线索 |
|---|---|---|
| Web 应用 | 兽型 | 前端框架依赖（React/Vue）、服务端框架 |
| 工具/CLI | 鸟型 | bin 入口、CLI 依赖（commander/click） |
| 库/框架 | 元素型 | package 发布配置、被依赖数 |
| AI/数据 | 龙型 | ML 依赖（torch/tf）、notebook 占比 |
| 移动端 | 飞行型 | Android/iOS 工程结构 |
| 游戏/图形 | 幻兽型 | 游戏引擎依赖、shader/渲染关键词 |
| 文档/博客 | 精灵型 | Markdown 占比极高、静态站点生成器 |

**完整品种 = 属性 + 类型**，例如："水系龙型"（Python 写的 AI 库）、"雷系兽型"（JS Web 应用）。属性×类型组合出 9×7 ≈ 60+ 基础品种，每种有专属立绘模板。

## 4. 品质体系（代码质量决定稀有度）

品质回答一个问题：**这个仓库的代码写得有多好？**

### 4.1 品质评分维度（Quality Score，0–100）

| 维度 | 权重 | 数据来源 |
|---|---|---|
| 测试完备度 | 25% | 测试文件占比、测试框架依赖、覆盖率徽章 |
| 工程质量 | 20% | CI/CD 配置、linter/格式化配置、类型注解 |
| 文档完整度 | 20% | README 丰富度、LICENSE、CHANGELOG、贡献指南 |
| 维护健康度 | 20% | issue/PR 关闭率、近半年活跃度、release 规范性 |
| 社区认可 | 15% | star、fork、被依赖数 |

### 4.2 品质档位

| 品质 | 名称 | Quality Score | 卡包视觉 |
|---|---|---|---|
| N | 普通 | 0–39 | 灰白卡包 |
| R | 稀有 | 40–59 | 蓝色卡包 |
| SR | 史诗 | 60–79 | 紫色卡包 |
| SSR | 传说 | 80–100 | 金色卡包，开包特效拉满 |

> 品质**动态变化**：质量提升可升阶，烂尾荒废会跌品质——让"还债"（补测试、写文档）有即时正反馈。
>
> **AI 率不进品质分**（v0.5 决策）。品质衡量"结果好不好"，AI 率衡量"底子稳不稳"——把 AI 率塞进品质会变成道德审判，也会误伤用它正经做重构的人。AI 率只经由 §6.3 的**根基**与 §6.4 的**词条**影响长线战力。

## 5. 等级体系（工程量决定初始等级）

等级回答另一个问题：**这个仓库做了多少东西？**

### 5.1 工程量估算模型

```
EngineeringScore =
    有效代码行数(LOC, 排除空行/注释/vendor)  × 权重A
  + commit 总数（近 2 年加权，近期权重高）     × 权重B
  + 源文件数                                  × 权重C
  + 贡献者人数                                × 权重D
  + 项目年龄（活跃月数）                       × 权重E
```

各项先做**对数归一化**（防止巨型 monorepo 碾压一切），再加权合成。

### 5.2 初始等级映射

| EngineeringScore | 初始等级 | 阶段 |
|---|---|---|
| 0–19 | Lv.1–49 | 幼体 |
| 20–39 | Lv.50–149 | 幼体 |
| 40–59 | Lv.150–299 | 成长体 |
| 60–79 | Lv.300–499 | 成长体 |
| 80–94 | Lv.500–799 | 完全体 |
| 95–100 | Lv.800–999 | 完全体 |

> 关键设计：**工程量只决定初始等级，等级上限 Lv.999 不封顶于出生**。老项目出生就是高等级完全体（尊重积累），新项目从幼体开始养（享受过程）。

### 5.3 出生后成长（XP 来源）

- 新 commit：+2 XP/个（每日上限 20）
- 关闭 issue：+5 XP
- 合并 PR：+10 XP
- 发布 release：+50 XP
- 新 star：+1 XP/个
- 连续 30 天无活动：进入「沉睡」状态，停止成长、外观萎靡

## 6. 能力值与技能

### 6.1 六维个体值（0–100，映射 S/A/B/C/D）

| 维度 | 数据来源 |
|---|---|
| 攻击（产出力） | 近 90 天 commit 频率 |
| 防御（稳定性） | CI、测试占比、release 规范性 |
| 速度（敏捷度） | issue/PR 平均关闭时长 |
| 特攻（技术深度） | 依赖数、技术栈丰富度 |
| 特防（可维护性） | 文档、注释率、代码复杂度 |
| HP（生命力） | 仓库年龄 + 持续活跃月数 |

> 个体值受品质加成：SSR 精灵六维上限更高（类似宝可梦的种族值差异）。
> 六维之上还有一层**根基**（§6.3）与**性格词条**（§6.4）：六维说"现在多强"，根基说"底子多稳"，词条说"脾气如何"。最终展示的数值 = 六维 × 词条修正。

### 6.2 技能

初始 2 个技能，随等级解锁至 4 个。技能由品种（属性+类型）生成，如：

- 水系龙型（Python AI 项目）：`张量洪流`、`梯度俯冲`、`数据缠绕`
- 雷系兽型（JS Web 项目）：`全栈突袭`、`npm 风暴`、`热更新闪避`
- 钢系元素型（Rust 库）：`所有权锁链`、`零成本抽象`

规则模板生成 + LLM 润色文案。

### 6.3 根基（隐藏第七维）

六维回答"它现在有多强"，**根基**回答另一个问题：**改动它要付多少代价。**

根基不画进雷达图，也不直接决定品质——它是一层"底盘"，只在三个地方生效：触发词条（§6.4）、抬高成长成本、影响重扫描时的数值稳定性。

#### 计算公式（0–100）

| 维度 | 权重 | 数据来源 | 含义 |
|---|---|---|---|
| 测试承重 | 30% | 测试文件占比，25% 封顶 | 动手时有没有安全网 |
| 提交粒度 | 20% | 平均代码行/提交：80 行满分，600 行以上归零 | 小步提交 = 可回滚 |
| 时间沉淀 | 15% | 仓库年龄 / 60 个月 | 活得久 = 坑都踩过 |
| 设计文档 | 20% | README 字数 60% + LICENSE 20% + docs 目录 20% | 别人能不能接手 |
| 真实性 | 15% | `100 − AI 味`（§12）；未检测时取中性值 65 | 每一步是不是人真的走过 |

**AI 率上限压制**（v0.5）：AI 味 ≥60 → 根基封顶 **55**；≥80 → 封顶 **38**。
换句话说：AI 味高的仓库，无论测试写得多齐，也别想拿"稳固"。

#### 分档

| 根基 | 档位 | 观感 |
|---|---|---|
| 80–100 | 稳固 | 底盘扎实，改哪儿都不慌 |
| 60–79 | 尚可 | 能维护，偶有暗坑 |
| 40–59 | 松动 | 一改就出连锁反应 |
| 0–39 | 根基不稳 | 外表光鲜，内部已经在晃 |

> **为什么是"压根基"而不是"扣品质"**：AI 辅助写出来的仓库通常配置齐全（CI / lock / 类型注解）、文档漂亮，品质分往往不低；它真正的代价在**改动成本**——没人走过每一行，边界条件靠猜补，重构时容易塌。做成"品质高、根基虚"的双层结构，既承认产出，也保留长线代价，比一刀切扣分更接近真实体感。
>
> 数值例子：AI 味 70 的仓库，品质 78（SR）照旧，但根基被压到 55、词条带上「根基不稳」→ 六维 −8%、升级需求 +15%。玩家想让它变强，最优解不是继续催 AI 写，而是补测试、拆提交、人工重构——这正是产品想引导的行为。

### 6.4 性格词条

词条是精灵的"脾气"：同样是 SR，一只「测试苦行僧」和一只「根基不稳」，长线表现完全不同。

四条设计原则：

1. **判出来，不是抽出来** —— 每个词条都有明确阈值与理由文案，展示给用户的是"因为你 X，所以有 Y"，不是随机 roll。
2. **可修复** —— 负面词条对应一个具体动作（补测试、推代码、拆提交），做完下次同步自动消失。
3. **负面优先** —— 最多 4 条，先排负面再排正面；同一个信号只触发一个词条（「生成体」替代「根基不稳」，不叠加）。
4. **确定性** —— 同一份快照必然得到同一组词条，不参与随机种子，避免"刷新刷词条"。

#### 负面词条

| 词条 | 触发条件 | 效果 | 怎么消掉 |
|---|---|---|---|
| **根基不稳** | AI 味 50–74 | 六维 −8%，经验需求 +15%，进化里程碑 +1 | 人工重构 + 补测试，把 AI 味压到 50 以下 |
| **生成体** | AI 味 ≥75 | 六维 −12%，经验需求 +25%，里程碑 +2 | 同上，压到 50 以下 |
| 裸奔无测试 | 测试占比 <3% 且代码文件 ≥10 | 防御 −15 | 补测试到 3% 以上 |
| 巨提交史 | 平均 >600 行/提交 | 速度 −8 | 靠后续小提交摊薄（连续 20 次小提交后消退，P1） |
| 沉睡症 | >180 天未推送 | 速度 −20，HP −10 | 推一次代码 |
| 孤岛项目 | 单贡献者 + 无合并 PR + open issue ≥20 | 特攻 −8 | 关 issue、引入贡献者 |
| 半途而废 | 仓库已归档或 Fork | HP −12，攻击 −8 | 解除归档 / 回到原创仓库 |
| 依赖臃肿 | 直接依赖 >60 | HP −8 | 清理依赖 |

#### 正面词条

| 词条 | 触发条件 | 效果 |
|---|---|---|
| 测试苦行僧 | 测试占比 ≥25% | 防御 +12 |
| 文档洁癖 | README ≥3000 字且存在 docs 目录 | 特防 +10 |
| 卷王 | 近 90 天 ≥60 次提交 | 攻击 +10 |
| 稳如老狗 | 提交 ≥100、平均 ≤120 行/提交、去年 ≥2 次发版 | 防御 +6，HP +5 |
| 开源传教士 | 贡献者 ≥10 且 issue 关闭率 ≥70% | HP +8 |
| 独行侠 | 单贡献者但 star ≥50 | 特攻 +8，特防 −4 |
| 十年老店 | 仓库年龄 ≥60 个月 | HP +10 |
| 双修 | 双属性精灵 | 特攻 +6 |

#### 数值叠算顺序

```
最终六维 = clamp( 原六维 × (1 + Σ statsPct/100) + Σ 定向修正 , 5, 100 )
每级所需经验 = 100 × level^1.5 × (1 + Σ expPct/100)
进化里程碑需求 = 基础里程碑数 + Σ milestone
```

- `statsPct`：全局百分比（目前只有 AI 词条用），先乘；
- 定向修正：直接加减某一维（如 防御 −15），后加；
- 夹在 5–100，避免出现负战力或溢出；
- 经验与里程碑修正只影响**成长速度**，不影响已有的等级与品质。

> 平衡意图：AI 词条是"**短期爽、长期贵**"——开包时数值好看、品质不低，但升级慢、进化难、根基虚。它不惩罚使用 AI，只惩罚"只用了 AI 而没有自己走过一遍"。

## 7. 养成与进化玩法

### 7.1 三阶段进化

```
幼体 → 成长体（Lv.150+ 且达成里程碑①）→ 完全体（Lv.500+ 且达成里程碑②）

> 等级上限 **Lv.999**。成长曲线为长期设计：经验需求随等级指数增长（`next_level_exp = 100 × level^1.5`），高等级后每一级都是真功夫，Lv.999 是传说级成就，全服屈指可数。
```

里程碑示例：首次 release / 贡献者 ≥5 / star 破百 / 测试覆盖率达标。

### 7.2 互动养成

- **每日投喂**：今日仓库有 commit = 喂了饭，额外 XP 加成
- **训练任务**：每周系统派发任务（"补一个测试"、"更新 README"、"关闭一个 issue"），完成奖励 XP
- **羁绊值**：互动频率累积，解锁称号与皮肤

### 7.3 分享卡片

一键导出精灵卡片（立绘 + 六维雷达图 + 品质 + 等级），支持嵌入 README 的动态 SVG。

### 7.4 竞技场对战（v0.3 新增，v0.5 扩展三种挑战）

进入竞技场先选挑战方式（`src/components/Battle.jsx`）：

- **在线对手**：两种规格——
  - **单项目**：输入对方 GitHub / Gitee 仓库 → `scanRepo()` 现场扫描 → `judge()` 生成对手，按仓库真实数值打，不叠难度，1v1；
  - **整仓**：输入对方账号（填仓库则按它的账号算）→ `scanOwnerBox()` 扫该账号的项目，按战力取前 3 组队，对手几只我方就上几只；

  命中 `src/rivals.js` 内置快照的仓库 / 账号可离线直取。在线对战经验基数：单项目 200 / 整仓 280。
- **同类型对战**：只从和先发精灵同属性（主属性优先、副属性补充）的知名仓库里挑对手，克制关系一目了然。
- **随机宠物**：内置对手池全体随机抽取（Fisher–Yates + 显式种子）。

后两种可选三档难度，倍率实打实乘到对手六维与等级（`scaleRival()`：×0.65 / ×1 / ×1.35，六维夹 6–150）。对手人数始终等于玩家上场人数。

回合制 3v3（也支持 1v1 / 2v2），机制细节与借鉴边界见 [`docs/BATTLE.md`](BATTLE.md)。要点：

- **属性克制**：9 元素克制表（克制 ×2 / 微弱 ×0.5 / 无效 ×0，双属性连乘）。一条免疫致敬原作：地免疫雷。
- **伤害公式**：沿用 Pokémon Showdown 的 Gen5 公式 `floor(floor(floor(2L/5+2) × 威力 × A/D)/50)+2`，战斗等级固定 Lv.50，再乘 STAB ×1.5、克制、会心 ×1.5、随机 0.85–1。HP = 60 + HP维 × 1.3。
- **技能槽**：4 槽对应 §6.2 的 4 技能——先制 45 / 主力 65 / 重击 95（会心率翻倍）/ 终极 120（反伤 1/4），解锁等级沿用 [1, 1, 150, 500]。
- **元素特性**（替代原作"特性/道具"位）：水潮汐自愈、雷静电蓄能、钢合金装甲、地厚土、岩岩壁、火灼热、风疾风、草生机、普通适应力。
- **异常状态**：灼烧（减攻 + 1/16）、中毒（1/8）、麻痹（减速 + 25% 失手）、沉睡（1–3 回合）。
- **能力等级**：−6..+6 分数表（Showdown 同款），由入场特性与AI行为触发。
- **行动顺序**：先制度 → 速度 → 种子随机；换人优先出手；全员无 PP 自动"挣扎"。
- **AI**：估伤 × 命中 + 斩杀奖励 + 少量噪声；血量 <30% 且替补属性更优时换人；三档难度只调换人概率与噪声。
- **结算**：胜负换 EXP（90/150/240 × 胜负系数）与羁绊，写回本地图鉴；同种子 + 同操作序列必然复现（`battle.js` 是纯函数 + 显式种子）。

> 设计取向：机制抄"骨架"（公式、顺序、状态机），数据层完全自研——GitMon 的精灵来自仓库快照，没有种族值/努力值/道具池，因此砍掉这几层，用元素特性顶上。官方引擎（`@pkmn/sim`，MIT）以 devDependency 接入做对拍：81 组克制、178 次伤害样本 0 差异（`npm run test:parity`），见 `docs/BATTLE.md` §7。

## 8. 系统架构（轻量方案）

### 8.1 设计原则

1. **一个进程跑全部**：单后端服务承载 API + 定时任务，无消息队列、无微服务。
2. **SQLite 起步**：单文件数据库，零运维；量大了再换 PostgreSQL，SQL 层保持兼容。
3. **无状态端点优先**：分享卡片、README 徽章都是"输入参数 → SVG/PNG"的纯函数，天然可缓存、可 CDN。
4. **重活异步化**：只有"扫描仓库"是重任务（浅克隆 + scc），用进程内任务队列串行消化，加超时与失败重试。
5. **一台 1C2G 服务器起步**，全部组件可塞进一个 Docker 容器。

### 8.3 模块拆解（7 个模块，边界清晰）

| 模块 | 职责 | 复杂度 |
|---|---|---|
| `scanner` | 解析 URL 识别平台 → 调 GitHub/Gitee API + 浅克隆跑 scc → 产出标准 `RepoSnapshot` | 中 |
| `engine` | 纯函数判定层：snapshot → 品种 / 品质分 / 工程量分 / 六维 / 技能。**零 IO，可单测** | 低 |
| `traits` | 纯函数：snapshot（+ ai_rate）→ 根基分档 / 性格词条 / 数值修正。**零 IO，可单测** | 低 |
| `aitrace` | 离线 AI 味检测：本地目录 → 五类信号 → 0–100 区间 + 证据。**零网络、零依赖** | 中 |
| `sprite` | 种子 → 像素精灵 PNG（移植 pixel-sprite-monster-generator 算法），磁盘缓存 | 中 |
| `api` | REST 端点：孵化、详情、图鉴、同步触发 | 低 |
| `badge` | 无状态 SVG/PNG 卡片端点，参考 github-readme-stats 架构 | 低 |

### 8.4 技术选型

| 层 | 方案 | 理由 |
|---|---|---|
| 前端 | React + Vite，静态托管 | 开包动画用 pack-opener-js（PixiJS），雷达图用轻量 SVG 自绘 |
| 后端 | Python **FastAPI** | 生态熟、scc 输出解析方便、APScheduler 内置定时 |
| 数据库 | **SQLite**（WAL 模式） | 单文件零运维；单写多读模型完全够用 |
| 代码统计 | **scc** 二进制调用 | 见 §10.5 |
| AI 味检测 | **自研 aitrace**（纯 Python 标准库） | 见 §12；零网络、可解释、可离线跑 |
| 定时任务 | APScheduler（进程内） | 不需要 Celery/Redis |
| 部署 | 单 Docker 容器（前端构建产物由后端直接托管） | 一条 `docker run` 上线 |

### 8.6 同步机制

- 首次孵化：实时扫描（任务队列，前端轮询/WebSocket 拿进度）→ 生成卡包
- 日常：每日定时同步已登记仓库，结算 XP 与品质变化
- 缓存：仓库快照缓存 6 小时（API 限流敏感）；精灵 PNG 永久缓存（种子不变图不变）
- 徽章端点：`Cache-Control: max-age=21600`，可直接挂 CDN

### 8.7 扩容路径（按需升级，不提前做）

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| L0 起步 | 单容器够用 | 现状 |
| L1 | 扫描变慢排队 | 扫描任务拆成独立 worker 容器（共用一个 SQLite→换 Postgres） |
| L2 | 徽章流量大 | 徽章端点前置 CDN，回源率极低 |
| L3 | 用户量上万 | SQLite → PostgreSQL，立绘迁移到对象存储 |

## 11. 同类产品参照与差异化分析

> 调研日期：2026-11-08。结论先行：**"仓库健康度宠物"已有先行者（github-tamagotchi 最完整），但"技术栈决定品种 + 代码质量定品质 + 卡包仪式感"这一组合是空白地带，是我们的差异化核心。**

### 11.1 直接竞品：仓库/编码宠物

| 产品 | 形态 | 核心机制 | 值得借鉴 | 短板/我们的机会 |
|---|---|---|---|---|
| **github-tamagotchi** ⭐最接近 | Web（FastAPI+Postgres） | 仓库健康度驱动宠物：commit/CI/release 加健康，PR 超 48h 宠物"焦虑"、issue 无人理"孤独"、依赖过时"生病"、安全告警扣血；6 阶段进化（蛋→长老）；健康归零 7 天死亡 + 纪念碑页 + 复活机制；AI 生成精灵；组织视图、排行榜、SVG 徽章、MCP 集成 | **情绪状态机**（饿/焦虑/孤独/生病）映射仓库信号的设计非常细腻；死亡/复活机制制造情感羁绊；"宠物性格由仓库 SHA-256 派生"与我们种子确定性思路一致 | 宠物形象**与仓库内容无关**（AI 随机生成）；无品质/稀有度概念；无开包仪式感；仅支持 GitHub |

## 12. 离线 AI 味检测工具（aitrace）

> 代码：`backend/gitmon_api/aitrace.py`（模块 + CLI），零第三方依赖、零网络、可单测。
> 一句话：**不联网、不调模型，只看本地代码的措辞、结构、命名、痕迹与提交历史，给出一个 0–100 的"AI 味"区间。**

### 12.1 定位与红线

它只服务一个用途：给 §6.3 的**根基**提供"真实性"信号。因此有五条红线：

1. **不联网** —— 只读本地文件，任何代码片段都不出机器。
2. **不调模型** —— 纯规则打分，千文件级仓库秒级出结果，可离线、可进 CI。
3. **不给判决** —— 输出区间 + 置信度 + 证据行号，不输出"这仓库是 AI 写的"。
4. **不对外展示原始分** —— 前端只显示「根基」和词条；AI 率是内部信号。把分数摊在明面上只会引发刷分对抗和人身攻击。
5. **可反驳** —— `--evidence` 打印到具体行，用户能指着一行说"这是我手写的"，我们据此调规则。

### 12.2 五类信号

| 类别 | 权重 | 看什么 | 典型命中 |
|---|---|---|---|
| **措辞** | 0.28 | LLM 的行文口头禅，按每千行命中密度计 | `Certainly` / `Here's` / `Note that` / `comprehensive` / `leverage`、`值得注意的是` / `综上所述` / `以下是一个` |
| **结构** | 0.22 | 注释率 >30%、每个文件都有模块 docstring、每个函数都有 docstring、空行率 >24%、每个文件都带 `if __name__ == "__main__"` demo 块 | "整齐得不像人写的" |
| **命名** | 0.14 | 泛化命名（`data`/`result`/`temp`/`value`）占比、四段以上长描述名（`calculate_total_price_with_tax`） | 语义正确但过于规整 |
| **痕迹** | 0.26 | AI 协作署名（`Co-authored-by: Copilot/Claude/Cursor/...`）、生成声明、占位实现、吞异常、空 catch、伪测试（`assert True`）、示例块、注释 emoji | 最硬的证据 |
| **历史** | 0.10 | git log：AI 署名比例、conventional commit 模板化率、单次 >800 行巨提交比例 | 提交流水 |

> 提交数 <5 时历史维度置空（一次导入的仓库没有统计意义），权重按剩余四项归一。
> 中文措辞权重 0.8：中文技术注释本来就爱用"首先/其次"，不能按英文标准算。

### 12.3 评分与输出

```
ai_rate = 100 × Σ(weight × score) / Σ(weight)        # 缺失维度自动从分母里去掉
```

**置信度**：<400 行 `low`，<2000 行 `medium`，否则 `high`；若命中家族 ≤1，降一级。

| AI 味 | 档位 | 含义 |
|---|---|---|
| 0–14 | 基本人工 | 几乎没有生成痕迹 |
| 15–34 | 轻度辅助 | 有 AI 参与，但被人改写过 |
| 35–59 | 大量辅助 | 结构由 AI 铺，人补细节 |
| 60–79 | 以生成稿为主 | 主体是生成的 |
| 80–100 | 几乎全生成 | 从骨架到注释都是一次性产出 |

### 12.4 用法

```bash
cd backend
python -m gitmon_api.aitrace ../                 # 人读报告
python -m gitmon_api.aitrace ../ --json          # 机器读（JSON）
python -m gitmon_api.aitrace ../ --evidence      # 带行号与命中片段
python -m gitmon_api.aitrace ../ --no-git        # 跳过 git 历史
```

对 GitMon 自身的实测输出（2026-11-08，54 个代码文件 / 6395 行）：

```
AI 味指数   12.9 / 100   ███·····················  基本人工
置信度     medium   代码 54 文件 / 6395 行   注释率 2.9%

信号分解
  措辞    6.3    权重 0.28  █···············
  结构    0.0    权重 0.22  ················
  命名   10.0    权重 0.14  ██··············
  痕迹   32.6    权重 0.26  █████···········
  历史    —      权重 0.10  （不可用，已按剩余权重归一）
```

> 置信度是 medium 而非 high，因为命中家族只有 3 个（措辞/命名/痕迹）——规则层的自我约束：证据不够多就不要装确定。

三种接入方式：

| 方式 | 场景 | 做法 |
|---|---|---|
| CLI | 本地自检 / CI 门禁 | `python -m gitmon_api.aitrace <本地仓库>` |
| 扫描钩子 | 线上孵化 | `GITMON_USE_SCC=1 GITMON_AI_TRACE=1`：浅克隆后顺手检测，写入 `snapshot.tree.ai_rate` |
| 纯函数 | 自定义流程 | `analyze_directory(path)` 返回完整结果，直接喂给判定引擎 |

### 12.5 误判与对抗（已知边界）

| 情况 | 处理 |
|---|---|
| 检测器自曝 | 含 `re.compile(` / `re.search(` / 规则表定义的行不计分——否则工具会把自己判成 AI 写的 |
| 文档里的 emoji | 文档类文件不计 emoji 痕迹，只算措辞与结构 |
| 生成物 / 锁文件 | 按后缀与名单排除（`.pb.go`、`_pb2.py`、`.min.js`、`package-lock.json` 等） |
| 一次导入的老仓库 | 提交数 <5 时跳过历史信号 |
| 中文注释的书面语 | 中文措辞权重 0.8，且文档类不计中文措辞 |
| 大规模重构 / 翻译 | 只给区间，不给结论；置信度 `low` 时判定引擎直接忽略该结果，不触发 AI 词条（已实现） |

### 12.6 校准记录

| 样本 | 规模 | AI 味 | 档位 | 判断是否符合直觉 |
|---|---|---|---|---|
| GitMon 自身 | 54 文件 / 6395 行 | 12.9 | 基本人工 | 是（AI 参与起草，但逐行重写过，痕迹集中在少数文件） |
| retort_engine | 233 文件 / 68477 行 | 8.7 | 基本人工 | 是（老代码库，注释率 0.3%） |
| 合成 AI 风格样本 | 1 文件 / 35 行 | 66.5 | 以生成稿为主 | 是（措辞与痕迹双高） |

### 12.7 与数值系统的接口

```
tree.ai_rate ──► §6.3 真实性维度（权重 15%）+ 上限压制（≥60 封顶 55，≥80 封顶 38）
             └─► §6.4 词条：≥50「根基不稳」，≥75「生成体」
未检测（None）──► 真实性取中性 65，不触发 AI 词条（宁可漏判，不可误伤）
```

## 13. 开放问题

1. ~~立绘方案~~ ✅ 已定（见 §10.3）：种子确定性像素精灵生成，替代原 SVG 拼装方案。
2. ~~AI 率怎么表达~~ ✅ 已定（见 §6.3 / §12）：只压根基与词条，不进品质分，不公开展示原始分。
3. **私有仓库**是否支持？需 OAuth，增加复杂度，建议后置。
4. 同一用户多只精灵是否需要**战队联动**玩法？
5. 远期是否引入**对战**？会影响数值平衡设计。
6. 产品名：GitMon / RepoMon / CodeSpirit / 代码精灵？
7. **Gitee 无 token 时的 API 限流**较严格（匿名配额低），是否需要引导用户授权？
8. **AI 味误判怎么兜底**？候选：低置信度不触发词条（P1）、用户一键申诉并冻结该维度、只展示根基不展示词条理由。
9. **AI 率的"洗白"路径**是否要显式鼓励？如"人工重构 200 行后 AI 味 −5"，或按最近 90 天提交加权（老代码不背锅）。
10. 词条上限 4 条够不够？负面词条过多会让新用户开包体验变差，需要观察。
