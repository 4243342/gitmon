# GitMon —— GitHub/Gitee 仓库精灵 · 产品设计文档

> 版本：v0.2
> 日期：2026-11-08
> 形态：Web 应用 | 数据源：GitHub + Gitee | 核心玩法：开卡包 → 养成进化

---

## 1. 产品概述

**GitMon** 是一个把代码仓库"孵化"为宝可梦式精灵的 Web 应用。

用户输入任意 **GitHub 或 Gitee** 仓库地址，系统扫描仓库后将其转化为一个**卡包**——打开卡包的瞬间，精灵破壳而出：

- **品种（种族/属性）** 由技术栈 + 项目类型决定
- **品质（稀有度）** 由代码质量决定
- **初始等级** 由工程量决定

开包即入册，此后仓库的每一次提交、每一个 release，都化为精灵的经验值，推动它升级与进化。

**一句话定位**：你的仓库，是一只活着的精灵；开包那一刻，它破壳而出。

---

## 2. 核心流程：从仓库到精灵

```
用户输入仓库 URL（GitHub / Gitee 自动识别）
        │
        ▼
┌─ 扫描引擎 ─────────────────────────────────────┐
│  ① 技术栈扫描：语言占比、框架依赖、项目类型       │
│  ② 工程量估算：代码行、文件数、commit、贡献者     │
│  ③ 代码质量评估：测试、CI、文档、复杂度、活跃度   │
└────────────────────────────────────────────────┘
        │
        ▼
生成「卡包」（卡包外观 = 品质预告，SSR 卡包金光闪闪）
        │
        ▼
用户点击「开包」→ 开包动画 → 精灵破壳登场
（品种 + 品质 + 初始等级 + 六维能力 + 技能）
        │
        ▼
进入「我的图鉴」，开始养成
```

### 2.1 双平台支持

| 平台 | 识别方式 | API |
|---|---|---|
| GitHub | `github.com/owner/repo` | GitHub REST/GraphQL API |
| Gitee | `gitee.com/owner/repo` | Gitee OpenAPI v5 |

统一抽象为 `RepoScanner` 接口，两平台各自实现，产出标准化的 `RepoSnapshot` 数据结构，后续判定逻辑与平台无关。

### 2.2 确定性原则

- 同一仓库同一时期的扫描结果生成**同一只精灵**：以 `platform/owner/repo` + 数据哈希为随机种子，不允许"刷初始"。
- 重新扫描只会更新等级/品质（养成结果），不会改变品种。

## 3. 品种体系（技术栈 + 项目类型）

精灵的"品种"由两个维度交叉决定：**元素属性**（主语言）× **生态类型**（项目类型）。

### 3.1 元素属性 —— 由主语言决定

| 主语言 | 元素属性 | 气质设定 |
|---|---|---|
| Python | 水 | 柔韧多变，数据与 AI 之灵 |
| JavaScript/TypeScript | 雷 | 敏捷爆发，无处不在 |
| Rust | 钢 | 坚硬安全，难以驯服但极可靠 |
| Go | 地 | 朴实稳重，并发之力 |
| Java | 岩 | 厚重耐久，企业级巨兽 |
| C/C++ | 火 | 原始强大，难以掌控 |
| Swift/Kotlin | 风 | 轻快现代，移动之翼 |
| Ruby/PHP | 草 | 优雅治愈，注重幸福感 |
| Shell/其他 | 普通 | 平平无奇，潜力未知 |

> 双语言仓库（占比均 >30%）生成**双属性精灵**。

### 3.2 生态类型 —— 由项目类型决定

通过依赖清单、目录结构、README 关键词、平台 topic 标签判定：

| 项目类型 | 精灵类型 | 判定线索 |
|---|---|---|
| Web 应用 | 兽型 | 前端框架依赖（React/Vue）、服务端框架 |
| 工具/CLI | 鸟型 | bin 入口、CLI 依赖（commander/click） |
| 库/框架 | 元素型 | package 发布配置、被依赖数 |
| AI/数据 | 龙型 | ML 依赖（torch/tf）、notebook 占比 |
| 移动端 | 飞行型 | Android/iOS 工程结构 |
| 游戏/图形 | 幻兽型 | 游戏引擎依赖、shader/渲染关键词 |
| 文档/博客 | 精灵型 | Markdown 占比极高、静态站点生成器 |

**完整品种 = 属性 + 类型**，例如："水系龙型"（Python 写的 AI 库）、"雷系兽型"（JS Web 应用）。属性×类型组合出 9×7 ≈ 60+ 基础品种，每种有专属立绘模板。

## 4. 品质体系（代码质量决定稀有度）

品质回答一个问题：**这个仓库的代码写得有多好？**

### 4.1 品质评分维度（Quality Score，0–100）

| 维度 | 权重 | 数据来源 |
|---|---|---|
| 测试完备度 | 25% | 测试文件占比、测试框架依赖、覆盖率徽章 |
| 工程质量 | 20% | CI/CD 配置、linter/格式化配置、类型注解 |
| 文档完整度 | 20% | README 丰富度、LICENSE、CHANGELOG、贡献指南 |
| 维护健康度 | 20% | issue/PR 关闭率、近半年活跃度、release 规范性 |
| 社区认可 | 15% | star、fork、被依赖数 |

### 4.2 品质档位

| 品质 | 名称 | Quality Score | 卡包视觉 |
|---|---|---|---|
| N | 普通 | 0–39 | 灰白卡包 |
| R | 稀有 | 40–59 | 蓝色卡包 |
| SR | 史诗 | 60–79 | 紫色卡包 |
| SSR | 传说 | 80–100 | 金色卡包，开包特效拉满 |

> 品质**动态变化**：质量提升可升阶，烂尾荒废会跌品质——让"还债"（补测试、写文档）有即时正反馈。

## 5. 等级体系（工程量决定初始等级）

等级回答另一个问题：**这个仓库做了多少东西？**

### 5.1 工程量估算模型

```
EngineeringScore =
    有效代码行数(LOC, 排除空行/注释/vendor)  × 权重A
  + commit 总数（近 2 年加权，近期权重高）     × 权重B
  + 源文件数                                  × 权重C
  + 贡献者人数                                × 权重D
  + 项目年龄（活跃月数）                       × 权重E
```

各项先做**对数归一化**（防止巨型 monorepo 碾压一切），再加权合成。

### 5.2 初始等级映射

| EngineeringScore | 初始等级 | 阶段 |
|---|---|---|
| 0–19 | Lv.1–49 | 幼体 |
| 20–39 | Lv.50–149 | 幼体 |
| 40–59 | Lv.150–299 | 成长体 |
| 60–79 | Lv.300–499 | 成长体 |
| 80–94 | Lv.500–799 | 完全体 |
| 95–100 | Lv.800–999 | 完全体 |

> 关键设计：**工程量只决定初始等级，等级上限 Lv.999 不封顶于出生**。老项目出生就是高等级完全体（尊重积累），新项目从幼体开始养（享受过程）。

### 5.3 出生后成长（XP 来源）

- 新 commit：+2 XP/个（每日上限 20）
- 关闭 issue：+5 XP
- 合并 PR：+10 XP
- 发布 release：+50 XP
- 新 star：+1 XP/个
- 连续 30 天无活动：进入「沉睡」状态，停止成长、外观萎靡

## 6. 能力值与技能

### 6.1 六维个体值（0–100，映射 S/A/B/C/D）

| 维度 | 数据来源 |
|---|---|
| 攻击（产出力） | 近 90 天 commit 频率 |
| 防御（稳定性） | CI、测试占比、release 规范性 |
| 速度（敏捷度） | issue/PR 平均关闭时长 |
| 特攻（技术深度） | 依赖数、技术栈丰富度 |
| 特防（可维护性） | 文档、注释率、代码复杂度 |
| HP（生命力） | 仓库年龄 + 持续活跃月数 |

> 个体值受品质加成：SSR 精灵六维上限更高（类似宝可梦的种族值差异）。

### 6.2 技能

初始 2 个技能，随等级解锁至 4 个。技能由品种（属性+类型）生成，如：

- 水系龙型（Python AI 项目）：`张量洪流`、`梯度俯冲`、`数据缠绕`
- 雷系兽型（JS Web 项目）：`全栈突袭`、`npm 风暴`、`热更新闪避`
- 钢系元素型（Rust 库）：`所有权锁链`、`零成本抽象`

规则模板生成 + LLM 润色文案。

## 7. 养成与进化玩法

### 7.1 三阶段进化

```
幼体 → 成长体（Lv.150+ 且达成里程碑①）→ 完全体（Lv.500+ 且达成里程碑②）

> 等级上限 **Lv.999**。成长曲线为长期设计：经验需求随等级指数增长（`next_level_exp = 100 × level^1.5`），高等级后每一级都是真功夫，Lv.999 是传说级成就，全服屈指可数。
```

里程碑示例：首次 release / 贡献者 ≥5 / star 破百 / 测试覆盖率达标。

### 7.2 互动养成

- **每日投喂**：今日仓库有 commit = 喂了饭，额外 XP 加成
- **训练任务**：每周系统派发任务（"补一个测试"、"更新 README"、"关闭一个 issue"），完成奖励 XP
- **羁绊值**：互动频率累积，解锁称号与皮肤

### 7.3 分享卡片

一键导出精灵卡片（立绘 + 六维雷达图 + 品质 + 等级），支持嵌入 README 的动态 SVG。

## 8. 系统架构（轻量方案）

### 8.1 设计原则

1. **一个进程跑全部**：单后端服务承载 API + 定时任务，无消息队列、无微服务。
2. **SQLite 起步**：单文件数据库，零运维；量大了再换 PostgreSQL，SQL 层保持兼容。
3. **无状态端点优先**：分享卡片、README 徽章都是"输入参数 → SVG/PNG"的纯函数，天然可缓存、可 CDN。
4. **重活异步化**：只有"扫描仓库"是重任务（浅克隆 + scc），用进程内任务队列串行消化，加超时与失败重试。
5. **一台 1C2G 服务器起步**，全部组件可塞进一个 Docker 容器。

### 8.2 总体架构

```
┌────────────────────────────────────────────────────┐
│                    用户 / 浏览器                     │
└──────┬───────────────────────────────┬─────────────┘
       │ Web 页面                        │ <img> 徽章
       ▼                                 ▼
┌──────────────┐                 ┌───────────────────┐
│  前端 SPA     │                 │  Badge 端点        │
│ (静态托管/CDN)│                 │  /badge/{repo}.svg │
└──────┬───────┘                 │  无状态·纯函数·可CDN│
       │ HTTP/JSON               └─────────┬─────────┘
       ▼                                   │
┌──────────────────────────────────────────┴─────────┐
│                 后端单体服务（FastAPI）                │
│  ┌────────────┐  ┌──────────────┐  ┌─────────────┐ │
│  │ API 层      │  │ 判定引擎      │  │ 立绘渲染     │ │
│  │ /hatch      │→ │ 品种/品质/等级│→ │ 种子→像素PNG │ │
│  │ /pet/{id}   │  │ 六维/技能    │  │ 预生成存文件 │ │
│  │ /sync       │  └──────▲───────┘  └─────────────┘ │
│  └────────────┘         │                           │
│  ┌────────────┐  ┌──────┴───────┐  ┌─────────────┐  │
│  │ 任务队列    │→ │ RepoScanner  │→ │ scc 二进制   │  │
│  │ (进程内)    │  │ GitHub/Gitee │  │ (浅克隆统计) │  │
│  └────────────┘  └──────────────┘  └─────────────┘  │
│  ┌────────────────────────────────────────────────┐ │
│  │ 定时任务（APScheduler）：每日同步 / XP 结算       │ │
│  └────────────────────────────────────────────────┘ │
└──────────────────────┬───────────────────────────────┘
                       ▼
              ┌─────────────────┐     ┌──────────────┐
              │  SQLite 单文件    │     │ 本地文件系统   │
              │  pets / logs    │     │ 精灵PNG/缓存  │
              └─────────────────┘     └──────────────┘
```

### 8.3 模块拆解（5 个模块，边界清晰）

| 模块 | 职责 | 复杂度 |
|---|---|---|
| `scanner` | 解析 URL 识别平台 → 调 GitHub/Gitee API + 浅克隆跑 scc → 产出标准 `RepoSnapshot` | 中 |
| `engine` | 纯函数判定层：snapshot → 品种 / 品质分 / 工程量分 / 六维 / 技能。**零 IO，可单测** | 低 |
| `sprite` | 种子 → 像素精灵 PNG（移植 pixel-sprite-monster-generator 算法），磁盘缓存 | 中 |
| `api` | REST 端点：孵化、详情、图鉴、同步触发 | 低 |
| `badge` | 无状态 SVG/PNG 卡片端点，参考 github-readme-stats 架构 | 低 |

### 8.4 技术选型

| 层 | 方案 | 理由 |
|---|---|---|
| 前端 | React + Vite，静态托管 | 开包动画用 pack-opener-js（PixiJS），雷达图用轻量 SVG 自绘 |
| 后端 | Python **FastAPI** | 生态熟、scc 输出解析方便、APScheduler 内置定时 |
| 数据库 | **SQLite**（WAL 模式） | 单文件零运维；单写多读模型完全够用 |
| 代码统计 | **scc** 二进制调用 | 见 §10.5 |
| 定时任务 | APScheduler（进程内） | 不需要 Celery/Redis |
| 部署 | 单 Docker 容器（前端构建产物由后端直接托管） | 一条 `docker run` 上线 |

### 8.5 核心数据模型

```
Pet {
  id, platform, repo_full_name, owner_user_id,
  element_type,        // 元素属性（主语言）
  species_type,        // 生态类型（项目类型）
  quality,             // N/R/SR/SSR ← 代码质量
  quality_score,       // 0-100
  level, exp,          // ← 工程量 + 成长（上限 Lv.999）
  engineering_score,   // 0-100
  stats {atk, def, spd, satk, sdef, hp},
  skills [],           // JSON 数组
  evolution_stage,     // 1/2/3
  seed, status, bond,
  sprite_path,         // 预生成 PNG 路径
  created_at, synced_at
}

GrowthLog { id, pet_id, event_type, xp_delta, created_at }
User     { id, github_login, gitee_login, created_at }   // P1 才需要
```

### 8.6 同步机制

- 首次孵化：实时扫描（任务队列，前端轮询/WebSocket 拿进度）→ 生成卡包
- 日常：每日定时同步已登记仓库，结算 XP 与品质变化
- 缓存：仓库快照缓存 6 小时（API 限流敏感）；精灵 PNG 永久缓存（种子不变图不变）
- 徽章端点：`Cache-Control: max-age=21600`，可直接挂 CDN

### 8.7 扩容路径（按需升级，不提前做）

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| L0 起步 | 单容器够用 | 现状 |
| L1 | 扫描变慢排队 | 扫描任务拆成独立 worker 容器（共用一个 SQLite→换 Postgres） |
| L2 | 徽章流量大 | 徽章端点前置 CDN，回源率极低 |
| L3 | 用户量上万 | SQLite → PostgreSQL，立绘迁移到对象存储 |

## 10. 开源资源调研与素材选型

> 调研日期：2026-11-08。结论先行：**开包动画有现成 MIT 库可直接用；卡面全息特效有标杆级参考（注意 GPL）；像素精灵可用种子确定性生成器；工程量统计用 scc。**

### 10.1 开包动画

| 方案 | 仓库 | 协议 | 评估 |
|---|---|---|---|
| **pack-opener-js** ✅ 首选 | npm `pack-opener-js`（PixiJS 渲染） | MIT | 专为开包场景设计：手指划开撕口、卡包盖飞出、卡牌带稀有度辉光翻面登场；支持 slice/burst/carousel 三种机制、200+ 可调参数、稀有度辉光色随品质切换；Web 与 React 组件双入口，也支持 React Native WebView。几乎是为我们量身定做的 |
| Pokemon-Pack-Sim | github.com/jaip18/Pokemon-Pack-Sim | MIT | React 19 + Framer Motion + React Three Fiber 的开包模拟器，有 3D 翻卡效果。功能完整但耦合 Pokémon TCG API，适合**参考动画编排**不宜直接引入 |
| pokemon-card-game | github.com/trungLyDal/pokemon-card-game | MIT | React + MongoDB 的开包+收藏全套实现（PackOpening 组件、卡册筛选），架构可借鉴，代码质量一般 |

### 10.2 卡面全息特效（品质视觉核心）

| 方案 | 仓库 | 协议 | 评估 |
|---|---|---|---|
| **pokemon-cards-css** ⚠️ 标杆参考 | github.com/simeydotme/pokemon-cards-css（8.3k⭐） | **GPL-3.0** | 纯 CSS（Transform + Gradient + Blend-mode + Filter）还原宝可梦剑盾时期全息闪卡效果，demo 见 poke-holo.simey.me，视觉效果天花板。**但 GPL-3.0 有传染性，不能直接搬代码进商业项目**——作为视觉参考自研实现 |
| **hover-tilt** ✅ | github.com/simeydotme/hover-tilt | MIT | 同一作者把卡片悬停倾斜+辉光效果抽成了独立 MIT 组件，效果接近、可直接用。N/R 卡用它，SR/SSR 再叠自研全息层 |

### 10.3 精灵立绘生成（品种视觉核心）

| 方案 | 仓库 | 协议 | 评估 |
|---|---|---|---|
| **pixel-sprite-monster-generator** ✅ 首选 | github.com/sempitern0/pixel-sprite-monster-generator | MIT（Godot 插件） | **种子确定性生成**像素怪兽：7 种体型（双足/四足/昆虫/史莱姆/有翼/魔像/幽灵）正好映射我们的生态类型，支持调色板控制（映射元素属性配色）、心情/恐怖/史诗变体（映射进化阶段）、PNG 导出。算法可移植到服务端预生成图库，与我们"同仓库必得同精灵"的确定性原则天然契合 |
| gen_me_a_pixamon | github.com/pixmusix/gen_me_a_pixamon | MIT | Rust 写的种子→像素怪兽 PNG 生成器，极轻量，单个 u64 种子产出确定立绘。可作服务端备选的轻量方案 |
| procedural-pixel-creatures | github.com/idlerunner00/procedural-pixel-creatures | 需核实 | C#/Godot，9 大族系+基因编辑+繁殖变异，质量高但引擎耦合重，适合远期参考 |

> **选型决策**：立绘方案从原草案的"SVG 拼装"改为**种子确定性像素精灵**。理由：像素风与宝可梦调性天然契合；种子确定性满足 §2.2；服务端一次性预生成 PNG，前端零渲染负担；规避 AI 生图的不可控与成本。

## 11. 同类产品参照与差异化分析

> 调研日期：2026-11-08。结论先行：**"仓库健康度宠物"已有先行者（github-tamagotchi 最完整），但"技术栈决定品种 + 代码质量定品质 + 卡包仪式感"这一组合是空白地带，是我们的差异化核心。**

### 11.1 直接竞品：仓库/编码宠物

| 产品 | 形态 | 核心机制 | 值得借鉴 | 短板/我们的机会 |
|---|---|---|---|---|
| **github-tamagotchi** ⭐最接近 | Web（FastAPI+Postgres） | 仓库健康度驱动宠物：commit/CI/release 加健康，PR 超 48h 宠物"焦虑"、issue 无人理"孤独"、依赖过时"生病"、安全告警扣血；6 阶段进化（蛋→长老）；健康归零 7 天死亡 + 纪念碑页 + 复活机制；AI 生成精灵；组织视图、排行榜、SVG 徽章、MCP 集成 | **情绪状态机**（饿/焦虑/孤独/生病）映射仓库信号的设计非常细腻；死亡/复活机制制造情感羁绊；"宠物性格由仓库 SHA-256 派生"与我们种子确定性思路一致 | 宠物形象**与仓库内容无关**（AI 随机生成）；无品质/稀有度概念；无开包仪式感；仅支持 GitHub |
| Repup (repup-cli) | 终端 CLI | 本地 .repup.json 存状态，commit 得 XP/等级/心情（EXCITED/SLEEPY），streak 追踪，零账号零数据库 | 极简主义证明：核心循环（ship→宠物开心）不需要重后端；心情文案人格化（"WE ARE SHIPPING."）是传播点 | 纯 ASCII 无视觉资产；本地状态无法分享；无品种概念 |
| cli-pet | 终端 CLI（TS） | 4 维状态（饥饿=commit、健康=CI 绿灯、快乐=PR 合并、精力=连续编码），7 种心情含"晕厥"，XP 升级 | 状态↔工程信号的四维映射简洁清晰，可参考进我们的六维体系 | 终端形态天花板低 |
| pixel-tamagotchi | 终端 TUI（Go） | 全局 git post-commit hook 感知提交，像素猫 4 种心情，零网络零依赖 | **git hook 触发**是零成本实时同步思路（可作为我们每日同步之外的即时反馈补充） | 单仓库本地玩具 |
| PokeToken | 桌面 App（Python/Tk） | Claude Code 的 token 消耗养成宝可梦：孵蛋（5M token/蛋，按捕获率加权稀有度）、真实进化链、25 种性格、隐藏 IV、1/64 闪光率、代币商店经济、连续打卡奖励 | **游戏系统完整度最高**：孵蛋加权、性格/IV/闪光、商店经济的数值设计可直接借鉴；用 PokéAPI 官方数据+立绘 | 消耗 token 越多宠物越强，激励方向存疑；非仓库维度 |

### 11.2 间接参照：开发者游戏化标杆

### 11.3 差异化定位总结

```
现有产品：宠物是"仓库健康的仪表盘"（拟人化监控工具）
GitMon：  精灵是"仓库的化身"（品种/品质/等级都由仓库本身决定）
```

| 维度 | 现有竞品 | GitMon 差异化 |
|---|---|---|
| 形象来源 | 固定几种 / AI 随机生成 | **技术栈×项目类型决定品种**，精灵即项目的"相" |
| 稀有度 | 无 | **代码质量定品质**（N→SSR），补测试写文档能升阶 |
| 仪式感 | 直接展示 | **卡包开启**动画，稀有度辉光 |
| 平台 | 仅 GitHub | **GitHub + Gitee 双平台**（国内开发者空白） |
| 传播 | README 徽章（github-tamagotchi 也有） | 徽章 + 精灵卡片 + 开包录屏天然适合短视频传播 |

> ⚠️ 风险提示：github-tamagotchi 已覆盖"健康度情绪宠物"心智且完成度高，我们**不应在"健康监控"维度正面竞争**，主打"开包收集 + 品种图鉴"的收集欲和"技术栈即品种"的认同感。
